AIに書かせた記事を機械で採点するスクリプトを自作しました。一文の長さ、同じ文末の連続、太字の数、漢字の比率。決めた条件に当てはまる箇所を数えて、合否を出します。

先日、それが「15項目すべて合格」と表示した記事を公開しました。あとで読み返すと、本文に「表の4つは」と書いてあります。記事のどこにも表はありませんでした。

このシリーズでは、自動化の戻り値だけでは実際の状態を判断できない場面を扱っています。1本目はデプロイ、2本目は `exit 0` と HTTP 200、3本目はブラウザ操作でした。4本目の対象は、自分で書いた検査スクリプトそのものです。

## 見逃していた5つの型

| # | 何が起きたか | 出力に現れた形 |
|---|---|---|
| 型1 | 見出し行を本文と1文に連結した | 60字超 29件 → 前処理を直して16件 |
| 型2 | 本の基準をそのままコードにして、普通の熟語を警告した | 6本中5本で警告 |
| 型3 | 数える単位を読み違え、記事全体で数えた | 6本合計で NG 12件 → 単位を直して7件 |
| 型4 | 自分で決めた除外を、一部の判定にしか通していなかった | 表示される字数が実際より多い |
| 型5 | 探す正規表現の範囲外は、そもそも見えていなかった | 「該当なし」として合格 |

型1から型3は、出た数字がおかしいと気づいて原稿や原文にあたれば辿り着けます。型4と型5は、出た数字そのものが自然に見えるので、実装を読むまで分かりませんでした。

以下のコードは `checklists/gate.py` からの抜粋です。実際に踏んだ順ではなく、原因の位置ごとに並べています。字下げは詰めてあり、離れた行を並べている箇所があります。

## 何を作ったか

AIに書かせる本数を増やすと、書く速さより読む速さのほうが先に足りなくなります。1本を人がていねいに読めば欠陥は見つかりますが、本数が増えると読み切れません。

そこで、機械で測れるものだけを機械に渡しました。判断が要るところだけ人が見る。そういう分担のつもりでした。実際には、機械に渡した側が壊れていました。

```console
$ python checklists/gate.py drafts/note-04-inspection-tool-blindspots/draft.md

=== drafts/note-04-inspection-tool-blindspots/draft.md  本文3232字 / 104文 ===
  [OK] A-1 60字超なし: []
  ...
  [OK] A-2 平均文長<=50: 31.1
  ...
  [OK] K-2 太字<=3箇所/見出し: 最多「検品する側を検品する2つの方法」2箇所 / 記事計4
  ...
  [OK] K-5 漢字比率<=35%: 33.4%
  ...
>>> 21項目を判定 / 合格 21 / 不合格 0
```

`...` は省略した行です。実際は21行が並びます。

## 型1：見出し行が本文と連結して、正しい原稿を弾く

「一文が60字を超えている箇所が29件ある」とスクリプトが返しました。原稿を開くと、指摘された箇所のうち13件は、本文の側に60字を超える文がありません。

文に割る処理は、句点の直後で切っているだけです。

```python
import re

text = "## 見出しに句点は打っていない\n本文はここから始まります。"
print([s for s in re.split(r'(?<=[。！？])', text) if s.strip()])
# → ['## 見出しに句点は打っていない\n本文はここから始まります。']  ← 30字の1文
```

見出しに句点を打っていなかったため、区切りが見出しをまたぎます。その結果、見出しと次の段落が1つの文として数えられていました。行頭が `#` や `-`、`|` の行を落としてから文に割るように直すと、29件は16件になりました。

減った13件は原稿ではなく、こちら側の誤りです。指摘のとおりに直していたら、正しい本文に手を入れるところでした。

## 型2：本の基準を、そのままコードにする

文章術の本に「漢字が続きすぎたら、ひらがなに開く」という助言があります。これを、そのまま判定にしました。

```python
KANJI_RUN_MAX = 4
kanji_runs = re.findall(r'[一-鿿]{%d,}' % (KANJI_RUN_MAX + 1), body)
```

6本にかけると5本で警告が出ます。中身はこれでした。

```python
>>> re.findall(r'[一-鿿]{5,}', "個人事業主の業務自動化と助成金報告書")
['個人事業主', '業務自動化', '助成金報告書']
```

ひらがなに開くと、かえって読みにくくなる語ばかりです。本が指しているのは、その場でつないだ語のことでした。定着した熟語と区別するには語のリストが要ります。この項目にはそれを持たせていませんでした。合否から外し、件数を出すだけに変えました。

## 型3：数える単位を読み違える

太字の数にも上限を入れました。6本にかけたところ、記事全体で数える設定では5本が違反で、最大は34箇所です。

厳しすぎるように見えたので原文を読み直すと、「1記事または1章につき3箇所」と併記されていました。記事単位でも章単位でも読める書き方です。章ごとに数えるほうへ変えます。

```python
bold_by_sec, cur = {}, '(リード)'
for line in raw.split('\n'):
    h = re.match(r'^##\s+(.*)', line)
    if h:                                   # H2 が来たら数える箱を切り替える
        cur = h.group(1)[:18]
        bold_by_sec.setdefault(cur, 0)
        continue
    if line.lstrip().startswith('|'):       # 表の行は数えない
        continue
    bold_by_sec[cur] = bold_by_sec.get(cur, 0) + len(re.findall(r'\*\*[^*\n]+\*\*', line))
```

出力が「どの見出しに何箇所あるか」まで具体化しました。6本合計で12件あった不合格は7件になります。消えた5件は、記事全体で数えたせいで出ていたものです。上限の3という数字を緩める前に原文へ戻ったので、残りの7件は違反として残りました。

## 型4：自分で決めた除外を、一部にしか適用しない

「冒頭の導入は500字以内」という項目があります。このスクリプトは、記事の先頭に置く設定情報（frontmatter）を本文から取り除く処理を持っています。

```python
def clean(t):
    t = re.sub(r'\A---\n.*?\n---\n', '', t, flags=re.S)  # Zenn frontmatter を除外
```

ところが冒頭の字数を数える行は、除去したあとの `t` ではなく、除去する前の `raw` を見ていました。

```python
fh = raw.find('\n## '); lead = len(re.sub(r'[#\s]', '', raw[:fh])) if fh > 0 else 0
```

Zennに出した3本で測ると、この設定情報は151字・134字・129字です。冒頭に使える実際の字数は500字ではなく、349字・366字・371字でした。基準の数字は正しく、除外の処理もあって、その2つがつながっていませんでした。

この誤りは、表示された数字を見ても分かりません。真の字数が基準の内側でも、設定情報を足した合計が500字を超えれば落ちます。

```console
（真のリード421字 ＋ 設定情報129字 の原稿を通した結果）
  [NG] D リード500字以内: 550
```

421字は基準の内側です。それでも550と表示されて落ちました。手元の3本は、たまたまこの帯の外にいただけです。

### この3つの数字は、一度取り違えている

151・134・129は、この記事を書きながら測り直した値です。最初は152・135・145と書いていました。手元の記録に「2026年8月3日に実測」とあったからです。

git で追うと、そのうち2つは**測定日の2日前に書き換えたタイトル**を含む、古い frontmatter の値でした。残る1つはどの時点にも一致しません。frontmatter そのものは、測定日から今日まで1バイトも変わっていません。「あとで変わった」でも説明がつきませんでした。

実測値に日付を添えても、対象が動くものなら再現できません。commit を書いておく必要がありました。

## 型5：探す範囲そのものに穴が空く

見出しの階層が飛んでいないかを見る項目があります。大見出しの次に、2つ下の見出しがいきなり来ていたら警告する、という判定です。

この判定は、見出しを探す条件が4段までしか書かれていませんでした。

```python
>>> md = "#### 四段目\n###### 六段目\n"
>>> re.findall(r'^(#{1,4}) ', md, flags=re.M)      # 旧
['####']
>>> re.findall(r'^(#{1,6}) ', md, flags=re.M)      # 新
['####', '######']
```

見出しが1つしか見えなければ、比べる相手がいないので飛びは検出されません。

```python
>>> jump = lambda hs: any(len(hs[i+1]) - len(hs[i]) > 1 for i in range(len(hs)-1))
>>> jump(['####'])                  # 旧: 飛びなし＝合格
False
>>> jump(['####', '######'])        # 新
True
```

5段目と6段目は、そもそも見出しとして数えられません。4段目から6段目への飛びは「そこに見出しがない」と扱われ、その飛びについて何も言わないまま通ります。手元の記事が4段目までしか使っていなかったため、この行を書いてから直すまでの15日間、誰も気づきませんでした。

### 同じ上限が、もう1か所に書いてあった

前に直したとき、同じ「4段まで」の条件がもう1か所にも書かれていることに気づいていませんでした。見出しを集める `heads` と、本文をブロックに割る `blocks` の2か所です。直したのは前者だけでした。

```python
>>> t = "##### 五段目の見出し\n本文はここから始まります。"
>>> re.split(r'^#{1,4} .*$|\n\s*\n', t, flags=re.M)     # 見出し行が残る
['##### 五段目の見出し\n本文はここから始まります。']
>>> re.split(r'^#{1,6} .*$|\n\s*\n', t, flags=re.M)
['', '\n本文はここから始まります。']
```

残った見出し行は、句点を持たないまま次の段落とつながります。型1がそのまま再現します。

```text
旧: [(27, '##### 五段目の見出し\n本文はここから始まります。')]
新: [(13, '本文はここから始まります。')]
```

この記事を書きながら調べて、ようやく見つけて直しました。1か所目を直した時点で「解決した」と記録していたので、残りの1か所は誰にも数えられていませんでした。

### さらに、記法そのものを見ていなかった

この原稿を別のAIに読ませて限定条件を出させたところ、もう1つ挙がりました。Markdownには、見出しの下に記号を並べて見出しにする書き方（Setext）があります。手元のスクリプトは、その形をまったく拾いません。

```python
>>> st = "五段目に相当する見出し\n---------------\n本文はここから始まります。"
>>> re.findall(r'^(#{1,6}) ', st, flags=re.M)
[]
>>> re.split(r'^#{1,6} .*$|\n\s*\n', st, flags=re.M)
['五段目に相当する見出し\n---------------\n本文はここから始まります。']
```

見出しの文字がそのまま本文として数えられ、試した原稿では漢字の比率が基準を超えて不合格になりました。閾値の近くにいる原稿だけが落ちるので、手元の40本では3本が反転します。

型1の対策も、ここでは効きません。落としているのは行頭が `#`、`-`、`|` の行です。Setext の見出しは、その本体がただの平文行なので落ちません。下線の `---` だけが消えて、見出しの文字は本文に残ります。5段目を直したあとも、探す範囲には穴が残っていたことになります。

## 全項目に緑が並んでも、記事は壊れていた

冒頭の話に戻ります。「表の4つは」と書いてあるのに表が無い記事は、当時の15項目すべてに合格していました。投稿先のエディタに表の機能がなく、書いたあとで箇条書きに直したなごりです。

一文の長さも漢字の比率も同じ文末の連続も測っていました。どれも合格です。書いてあることと実物が一致しているか、という項目を持っていませんでした。

持っていない項目は、不合格になりません。結果の画面に「これは測っていない」とも出ません。

現在は21項目まで増やしましたが、増えた6項目にも、この欠陥を見つけるものはありません。しかも21項目のうち4つは、件数を出すだけで不合格を出さない項目です。実際に落ちる可能性があるのは17項目でした。

```python
res = [('A-1 60字超なし', not long_s, ...),
       ...
       ('K-6 漢字5連続(参考)', True, f'{len(kanji_runs)}件 {kanji_runs[:4]}'),
       ('K-7 体言止め(参考)', True, ...),
       ...
       ('K-12 重複段落(参考・要目視)', True, ...),
       ('K-13 数字なしH2(参考・体験/固有名詞で担保されているか確認)', True, ...)]
```

第2要素が合否です。`True` が直書きされている4項目は、何を渡しても落ちません（`...` の位置には、合否を出す項目が入ります）。合計欄の「21項目を判定」は、この4つを含んだ数字です。

## 5つに共通していたこと

走査した件数を出さない道具では、探す条件が狭いと「該当なし」だけが返ります。エラーではありません。見つからなかったのか、そもそも探していないのか、出力からは見分けられません。5段目の見出しを拾わなかった件がこれにあたります。

レビューもテストも通していない自作の検査は、盲点が作った本人の思い込みと同じ形をしています。見出しに句点を打たないことも、章ごとに数えることも、書いた本人が見落としたままコードになりました。

そして「全項目合格」は、測れる範囲に問題がない、という意味ですらありません。型5のように、項目が存在していても中身が範囲を取りこぼしていることがあります。合格が言えるのは、その実装が見た範囲では引っかからなかった、というところまでです。

## 検品する側を検品する2つの方法

1つは、壊した原稿と壊していない原稿を対で通すことです。60字を超える文、飛んだ見出し、使わないと決めた語をあえて入れたダミーで、狙った項目が落ちるかを見ます。同時に見るのは、正常な原稿で余計な項目が落ちないかどうかです。壊した側だけだと、型1のような「正しい原稿を弾く」誤りが素通りします。

5段目の見出しを拾えていなかった件は、1か所目がこの方法で見つかりました。新しい項目を足すついでに、古い項目も試したときです。2か所目のほうは治具がまだ無く、この記事を書きながら手で追って見つけました。

もう1つは、基準をコードにする前に、実例で1回試すことです。漢字の連続も太字の件も、手元の原稿にあてれば数分で誤りが出ました。誤検知が出たときは、基準の数字を緩める前に、基準の読み方と実装の両方を見ます。

やっかいな点も1つあります。21項目の最新版で公開済みの記事を1本かけたところ、2項目が不合格になりました。公開した時点では合格していたものです。過去の成果物が満たしていなかった観点を新しく足すと、すでに出したものが落ちます。落ちた分をいつ直すかまで決めておかないと、不合格のリストだけが積み上がります。

## まとめ

検品の仕組みは、合格を出すためだけに持つものではありません。何を見ていないかを知るために、定期的に点検する対象でもあります。

外注先や社内のAI運用を確かめるときも、聞く順番は同じです。「どうチェックしていますか」の次に、「そのチェックが素通りさせたものはありますか」を置きます。素通りした例と、それをどうやって見つけたかを挙げられる相手は、自分の検査の範囲をつかんでいます。
