25件しか見えない一覧、1件しか返らないアクセシビリティツリー、実在する文字列を0件と返す検索。この3つではエラーが出ませんでした。4つ目はタイムアウトです。エラーは返りましたが、それでも何が起きたかは分かりませんでした。

このシリーズでは、自動化の戻り値だけでは実際の状態を判断できない場面を扱います。1本目はデプロイ、2本目は `exit 0` と HTTP 200、3本目がブラウザです。

成功が返っても、エラーが返っても、それだけでは実状態を確定できないことがあります。問題は操作の成否だけではありません。その後にエージェントが確定した「結果」の方でした。

| 観測された結果 | 実際に確認すべきこと |
|---|---|
| 取得できた | **全件**取得できたか |
| クリックできた | **正しい対象**をクリックしたか |
| 入力できた | **正しい文字列**が入ったか |
| タイムアウトした | 処理が**実行されたかどうか** |

以下は2026年7月22日から8月1日に実際に踏んだものです。**操作APIの戻り値だけでは実際の状態を確定できなかった例**で、網羅でも排他でもありません。複数が同時に起きることもあります。

件数・画面寸法・タイムアウト時間は実業務で記録した値です。割合はそこからの計算値です。Claudeの上限値とリサイズ仕様は公式ドキュメントに基づきます。対象はログイン必須なので再現手順は示せません。代わりに検算・計測コードを添えます。コード自体にも罠があるため、成立条件と崩れ方まで書きます。

## 症状1：取得成功 ≠ 全件取得

求人サイトの一覧をアクセシビリティツリー経由で読ませました。カテゴリを切り替えるたびに「該当1件」と返ります。エラーも警告もありません。実際には1ページ最大20件で、6ページ巡回すると合計102件ありました。

その一覧は仮想スクロールでした。確認時点では画面外の行がDOMから外れていました。返ってきた1件自体は実在する項目です。問題は、それを一覧全体として扱った瞬間に生じます。

別のWebアプリでも同型を踏みました。チャット一覧の初回DOMは25件です。スクロールを繰り返すと432件まで増えました。25件で確定していたら、実在する相手の94%を「いない」と判定していました。

ある求人サイトでは、「記事」と検索しても `SEO記事執筆` を含む案件が出ませんでした。少なくとも、文字列の包含だけで「無い」と判断できる検索ではありません。Googleスプレッドシートでも、Ctrl+F が `0/0` を返したのに、その文字列は実在していました。

**完全性を確認していない取得結果だけでは、不在は判断できません**。今回の検索では、該当なしは空の結果として扱われ、例外にはなりませんでした。

### 検算：母集団の側から数える

DOMから集めたURLの総数がサイト表示の全102件と一致し、ようやく「数えられた」と判断しました。ページごとの件数を足してはいけません。同じ案件が複数ページに出ると、重複は消えないからです。

数えるのは件数ではなくURLです。巡回中に見つけたURLを集合へ貯めます。

```js
sessionStorage.removeItem('__ew_jobAudit_v1');
```

> **これは監査の開始時に1回だけ実行します。下の収集コードを繰り返すときには実行しません。**

```js
(() => {
  const key = '__ew_jobAudit_v1';
  const urls = new Set(JSON.parse(sessionStorage.getItem(key) ?? '[]'));
  document.querySelectorAll('#job-list a[href^="/jobs/"]').forEach((a) => {
    urls.add(new URL(a.getAttribute('href'), location.href).href);
  });
  sessionStorage.setItem(key, JSON.stringify([...urls]));
  return urls.size; // 巡回中に観測したユニークURL数
})();
```

- 前提：同一オリジン・同一タブで巡回します（`sessionStorage` はリロードをまたいで残ります）。仮想スクロールでは、行がDOMから消える前に途中で何度も実行します。最後まで送ってから1回数えると、この記事の症状1を踏みます。同一案件に複数のURL表現があるなら案件IDで重複排除します。セレクタは対象サイトに合わせて変えます（例は `href` が `/jobs/` 始まりのサイト用です）。
- 限界：巡回中に掲載終了や新規追加があるサイトでは、同一時点のスナップショットではなく、巡回期間中に観測したURLの和集合になります。
- 崩れ方：拾い損ねると例外なしで過少に、リセットを忘れると例外なしで過大になります。ストレージが使えない場合や容量超過ではStorage APIが例外を返し、保存値が不正なJSONなら `JSON.parse()` で止まります。

一致は傍証であって証明ではありません。サイト表示のキャッシュや集計漏れは別に潰す必要があります。そのサイトは掲載16,267件と表示しながら、募集中では102件でした。割合は0.63%です。大きい数字は在庫とは限りません。

## 症状2：クリック成功 ≠ 対象選択成功

Googleスプレッドシートを座標クリックで操作させると、1行ズレて隣の行を選びました。そのままDeleteと入力が続き、既存データを上書きしました。

確認できたのは、座標系にスケール差があったことです。スクリーンショットは1568×744、実ビューポートは2231×1059でした。縦横とも約1.423倍です。

横方向にも40〜90px、最大でおよそ1列分ズレました。幅300pxを超える列では、同じ列内に収まることもあります。このセッションでは、幅80〜90px程度の列で隣の列まで入るケースがありました。

canvas描画が主体のアプリでは、個々の表示物をDOM要素として参照できないことがあります。筆者の環境では、セル群がアクセシビリティツリー上で1つのコンボボックスに見えます。そのため座標クリックが唯一の手段に見えて、その手段がズレていました。

Name Box（セル参照の入力欄）でも同型を踏みます。クリックがわずかに外れ、直前のセルが選択されたまま `W26` とタイプしました。このケースではキー入力が止まらず、その文字列が直前のセルへ入っています。

### 縮小がどこで起きたかは、切り分けていない

先に結論です。Claudeへ2231×1059の画像が渡っていたなら、標準ティアのリサイズで観測値を説明できます。高解像度ティアでは説明できません。ただし、渡る直前の画像寸法もモデルのティアも記録しておらず、原因は確定できていない状態です。

[Claude の座標仕様](https://platform.claude.com/docs/en/build-with-claude/vision-coordinates)では、上限を超える画像をアスペクト比を保って縮小します。返される座標は縮小後の画像が基準です。標準ティアは長辺1568px・視覚トークン1568、高解像度ティアは2576px・4784です。

公式のリファレンス実装に2231×1059を標準ティアで通すと、1568×744になります。観測値と一致します。高解像度ティアなら3040トークンで上限内なので縮小されません。

ただし、2231×1059は実ビューポートの値です。それがそのままClaudeへ渡ったとは確認していません。エージェント側で先に縮小された可能性も残ります。この一致だけで原因は決められません。

### 計測：ページ側の座標系を記録する

縮小率は期待値だけで決めず、実際に返った画像寸法と突き合わせます。

```js
// ページ側の値。スクリーンショット画像の実ピクセル幅・高さと別途比べる
JSON.stringify({
  innerWidth: window.innerWidth,
  innerHeight: window.innerHeight,
  dpr: window.devicePixelRatio,
});
```

- 前提：このコード単独では縮小率は確定できません。`innerWidth × devicePixelRatio` が画像の幅と一致するとは限りません（OSの表示拡大率や、渡す側の縮小が挟まります）。画像の実寸を別に記録し、縦横それぞれの比を出します。
- 崩れ方：例外は出ません。期待値だけで済ませると、誤った縮小率のまま座標を送り続けます。

運用では座標に頼らない方法を優先しました。Googleスプレッドシートなら、URLのフラグメントに範囲を書いて移動できます。

```text
https://docs.google.com/spreadsheets/d/<ID>/edit#gid=<GID>&range=A236:N260
```

形式を誤ってもエラーにならず、シートの先頭が開きました。移動後に現在位置を読み直します。セル移動も矢印キーやTabを優先します。先頭セルを誤って編集する事故を避けるためです。

## 症状3：入力成功 ≠ 値の一致

応募フォームに日本語の長文をタイプさせると、4箇所で欠落・置換・混入を確認しました。エラーは一切出ません。送信前に目視しなければ気づけませんでした。

```text
「24歳」   → 「7726歳」
「もうすぐ」 → 「もうすぇ」
「学生」   → 「字生」
「自由」   → 「目由」
```

同じ内容を値の直接設定で入れ直すと、このセッションでは欠損を再現しませんでした。

スプレッドシートのセルでも似た欠損が出ました。日本語をタイプすると、先頭2文字が落ちる現象が3回連続で再現しました。セルを選択してDeleteし、F2で編集モードへ入ります。その後にタイプし、Enterで確定すると落ちませんでした。

ただし、F2の直後に間を置かずタイプすると再発しました。編集モードへ入る前に入力が始まったためです。

あるサービスは「Shift + Enterで送信 / Enterで改行」と表示していました。一般的なチャットとは逆です。改行のつもりで押すと、そこまでの1行目だけが送信されました。送信後は入力欄がクリアされ、後続の入力は無視されました。投稿は編集も取り消しもできません。

### 検算：打った後に読み戻す

送信前に、入力欄の値を原文と突き合わせます。

```js
// 送信ボタンを押す前に、入力欄の値を原文と突き合わせる
const expected = `ここに送信予定の原文を入れる`;
const el = document.querySelector('textarea[name="message[body]"]');
const norm = (s) => s.replace(/\r\n?/g, '\n');
el === null
  ? 'NOT FOUND'
  : JSON.stringify({ ok: norm(el.value) === norm(expected), len: el.value.length });
```

- 前提：セレクタが外れると `el` は `null` になるので、比較の前に判定します。textarea の `value` は CRLF が LF に正規化されます。Windowsで作った原稿と比べるなら改行を揃えます。
- 崩れ方：nullチェックが無ければ例外で止まります（これは気づける方です）。改行を揃え忘れると、正しい入力を「不一致」と報告します。

値の直接設定も万能ではありません。Reactなどの制御された入力欄では、DOMの `value` を書き換えてもアプリ側の状態に反映されないことがあります。この場合、DOMの値を読み戻しても一致します。

読み戻しで分かるのはDOMの値までです。再レンダリング後も値が残るか、実際に送られた内容まで確認します。**手段を正解にせず、事後の確認を正解にします**。

全ての入力を読み戻すのは現実的ではありません。不可逆なもの、共有相手がいるもの、一括処理の起点になるものに限ります。そこでは、読み戻すまで完了と見なさない運用です。

## 症状4：タイムアウト ≠ 未実行

チャットへ送信させている最中に、ブラウザ側の実行が45秒でタイムアウトしました。使っていたのはChrome DevTools Protocol（CDP）です。返ってきたのは `The renderer may be frozen or unresponsive` でした。

これを「送信されなかった」と解釈して次の操作を投げました。しかし、タイムアウト後も送信処理は完了し、メッセージが着弾していました。「失敗したから再実行」と1回送り直していれば、二重送信でした。

送信・保存・投稿・決済のような副作用のある操作では、タイムアウトを「失敗」ではなく「不明」と扱います。成功と失敗の2値ではなく、**unknown を持つ**という扱いです。

次の操作の前に、画面か一覧を再取得して実測します。自動リトライで二重実行が起きる典型例が、処理は成功したのに応答だけが返らなかったケースです。

### 執筆中に踏んだ、状態が食い違う例

最小再現ページをローカルに作り、エージェント側のブラウザで開きます。`file://` へのナビゲーションは300秒でタイムアウトしました。

直後、タブ状態を返すAPIはoriginに目的のURLを表示しています。ところが同じタブでJavaScriptを実行すると、別の結果が返りました。

```text
tabs_context      → origin: file:///.../index.html
javascript_tool   → No site is open in this tab.
```

この2つだけでは、ページが開いていたかどうかは確定できません。スクリーンショットもDOMも取っていないからです。

確定できたのは、タブ状態を返すAPIとJavaScript実行APIで認識が食い違ったことだけです。どちらが正しいか決めずに進むと、以後の測定値が何に対するものか分からなくなります。

## なぜ気づけないのか

この4つは、「戻り値だけでは実状態を確定できなかったもの」という基準で選んだ事例です。共通点があるのは当然で、それ自体が発見ではありません。

理由は2つです。前の3つは成功と同じ形の結果を返しました。今回の検索では、該当なしも空の結果として扱われています。クリックは、当たっても外れても同じ戻り値でした。

4つ目は逆にタイムアウトという異常が返りました。それでも「未実行」までは意味しません。**操作そのものの戻り値だけでは検証できず、別経路で結果の状態を読み直す必要があります**。

もう1つは、エージェントでは誤りが増幅しやすいことです。誤った観測が自然な断定文へ変わり、その文章が次の操作の前提として再利用されます。

「25件見えた」が「25件存在する」に変われば、その誤差は次の検索・連絡・削除まで伝播します。

## 運用に落とした4つのルール

| 症状 | ルール |
|---|---|
| 件数 | 取得件数を存在件数として扱わない。母集団側の数字と突き合わせるまで確定しない（一致は傍証であって証明ではない） |
| 座標 | canvas描画アプリでは座標クリックを第一選択にしない。代替があればURL指定・キーボード移動を優先し、座標を使うなら操作後に現在位置を読み直す |
| 入力 | 不可逆・共有・一括処理の起点になる入力は、送信前に値を読み戻して原文と比べる。制御された入力欄なら送信内容まで確認する。長い日本語では文字単位のキー合成を避ける |
| 応答 | 副作用のある操作のタイムアウトは「不明」として扱う。実測するまで再実行しない |

この4つとは別に、実害を抑えるうえで最も効いたのは「一括処理の前に1件だけ流す」運用でした。二重連絡の事故を1件に限定できたのは、最初の1件を送ったあとに画面を確認していたからです。20件を同じ手順で流していれば全件で起きていたと思いますが、実際には流していないので確認はしていません。

4つのルールは誤りを検出する方法で、1件だけ流す運用は、誤りがあったときの被害範囲を抑える方法です。役割が違うため、両方が必要になります。

```text
対象サイト: Googleスプレッドシート、求人サイト、チャットWebアプリ（ログイン必須のため再現手順は非掲載）
```
